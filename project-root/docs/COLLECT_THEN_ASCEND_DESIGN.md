# 「先收集，再晋升」交互式流程设计

> 设计目标：把《诡秘之主》原著中**权柄之争 → 真神唯一 → 旧日超越序列**的硬设定，转化为 GUI 中可点、可感、有门控的交互流程，并真正接入已落地的 `uniqueness.py` / `pathway_groups.py` 模拟主流程。
> 设定来源：爱潜水的乌贼《诡秘之主》《宿命之环》；校验于萌娘百科「非凡途径/旧日」、百度百科「旧日」、Fandom 中文 wiki 等公开设定资料（检索于 2026-08-14）。

---

## 1. 原著设定锚点（设计的事实基础）

| 位阶 | 晋升条件（原著） | 本项目映射 |
|---|---|---|
| **序列0 真神** | 本途径**全部 3 份序列1非凡特性 + 1 份唯一性**（"3+1"），集齐后自行聚合；仪式仅辅助；**真神唯一**（每途径至多一位） | `ascension.ascend` 在 `next_level==0` 时自动绑定本途径唯一性 + 3 份序列1；GUI 增加"集齐后方可晋升"门控 |
| **唯一性** | 每途径有且仅有 1 份；容納方式有三（活化自带 / 强行收入体内压制 / 调和为魔药）；可随持有者意志变形 | `Uniqueness`（全局注册表 + 争夺 `bind`/`unbind`） |
| **序列1 天使之王** | 每途径至多 3 份序列1；持唯一性或多份特性者晋升为"天使之王"（准神） | `SequenceOneCharacteristic`（3 份库存 + 归属） |
| **旧日 / 序列之上** | **源质 + 相邻途径组全部唯一性 + 至少 1 份序列1**；**无需仪式**；最优容纳顺序：**先成序列0 → 融合源质 → 最后容纳其余唯一性** | `pathway_groups.promote_to_old_one`（聚合组内各途径唯一性 + 3 序列1） |
| **9 源质 / 9 权柄体系** | 9 源质对应 9 组相邻途径；地球上可诞生旧日共 9 位 | `PATHWAY_GROUPS`（9 组） |
| **三支柱 + 第四支柱** | 诡秘之主(源堡)、上帝(混沌海)、堕落母神(母巢) 为三支柱；永暗之河 + 灾祸之城 构成隐含第四支柱 | `FOUR_PILLARS`（`pathway_groups.py`） |

> **关键设定细节（决定交互节奏）**：旧日晋升**无须仪式**，且"容纳顺序"影响成功率——先成神、再融源质、最后纳其余唯一性为最优。这意味着 GUI 的旧日流程应呈现为"序列0 → 晋升旧日"的两段式，而非与中低序列那样走仪式链。

```
                                  │                       │

                                  │                 └────────┬────────┘

                                  │                   「聚合·晋升序列0」
                                  │                          │

```

## 3. 三段式交互设计详述

### 阶段 A：扮演消化 + 逐级晋升（既有，保留）
- 左栏选途径 → 生成序列9 角色。
- 中栏"操作"逐一点击扮演行为 → 消化度达 100% → 解锁「晋升至序列 N-1」按钮。
- 锚系统（≥序列5 需锚，序列0 需宏大锚定 ≥200）在此逐级校验，未达标优雅失败（不崩）。

### 阶段 B：序列1 → 序列0 的「权柄收集」（本次新增面板）
- **触发**：角色处于序列1 时，操作面板追加"权柄收集 · 旧日晋升"区块。
- **状态可视**：
  - 唯一性：空闲 / 你已持有 / 被[持有者]持有（真实读 `Uniqueness` 注册表）。
  - 序列1特性：你持有 X/3（全局空闲 Y）。
- **交互动作**：
  - `⚔ 争夺序列1特性`：依序容纳一份空闲序列1；若被他人持有，则"击败持有者并夺取"（单人模拟下的权柄之争）。
  - `🔒 容纳唯一性`：同理容纳本途径唯一性。
  - `⬆ 聚合·晋升序列0`：**仅当 3+1 全部归属当前角色时**才出现并可用。
- **门控安全**：直接点通用晋升按钮而未集齐权柄时，`_do_ascend` 会拦截并提示"需先在权柄收集面板集齐"，绝不静默放行。

> 与原著一致性：把"3+1 聚合"显式化为可操作的收集阶段，呼应"真神唯一、需夺齐权柄"的核心张力；"争夺/夺取"按钮即"权柄之争"的可玩化呈现。

### 阶段 C：序列0 → 旧日 的「旧日晋升」（本次新增面板）
- **触发**：角色处于序列0 时显示。
- **信息呈现**（来自 `OldOnePath.required_for_old_one`）：
  - 所属权柄体系（如"诡秘之主"组：愚者/门/错误）。
  - 源质（源堡）与层次（普通旧日 / 支柱级旧日）。
  - 需聚合的途径数与各途径唯一性+序列1 要求。
- **交互动作**：`🌟 容纳源质·晋升旧日` → 调用 `promote_to_old_one(group_key, character)`。
  - 成功：角色卡头部新增 `★ 旧日位阶：<体系>（支柱：<支柱名>）` 金标；日志打印聚合摘要。
  - 失败（权柄被占）：捕获 `SequenceError`/`RuntimeError`，日志红色提示"权柄争夺失败"，不崩。
- **支柱识别**：组 key 落在 `FOUR_PILLARS`（源堡/混沌海/母巢/永暗之河/灾祸之城）时标注"支柱级旧日"。

## 4. 状态与数据流

```
self.character   ── 当前序列实例（晋升时由 ascend 生成新实例）
self.old_one_info ── 晋升旧日后写入的构成摘要（group/tier/pillar/pathways[]）
                      切角色时由 set_character 清空，避免串味
```

- 收集进度**不另存副本**：面板直接读 `Uniqueness` / `SequenceOneCharacteristic` 全局注册表，保证"所见即所存"，且天然支持与其他角色/进程的权柄争夺一致性。
- 晋升序列0 前，GUI 会先 `_release_pathway_authority` 释放已收集权柄，交由 `ascend` 重新"聚合"到新神躯——精确对应原著"3+1 自行聚合"的机制。

## 5. 与原著的差异与可扩展点（诚实标注）

1. **相邻途径序列1 数量**：原著旧日只需相邻途径**各 1 份**序列1；本项目 `promote_to_old_one` 为简化实现，聚合了**各 3 份**。GUI 如实呈现项目模型——若追求考据精度，后续可把 `required_for_old_one` 改为"每途径 1 份"并相应调整面板文案。
2. **源质作为可收集对象**：原著旧日核心是"容纳源质"；本项目尚未把源质建模为可交互实体，`promote_to_old_one` 直接以"聚合唯一性+序列1"表征旧日化。增强方向：新增"源质收集"小游戏/事件，作为序列0→旧日之间的独立一步，强化"先成神→融源质→纳唯一性"的最优顺序叙事。
3. **单人模拟下的"争夺"**：当前"击败持有者夺取"是确定性夺取（无 rival AI）。可扩展为：引入 rival 天使之王 NPC，争夺触发概率/搏杀判定，让"权柄之争"真正有风险。
4. **封印物 crafting**：`sealed_artifact_level` 已按序列等级映射封印物等级，但尚未在 GUI 暴露"用多余特性锻造封印物"的入口，可作为后续面板。
