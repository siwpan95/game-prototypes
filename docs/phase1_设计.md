## 一、要加的五件事（用户拍板的"完整玩法"路线下的第一批）

| # | 能力 | 为什么是这一批 |
| --- | --- | --- |
| 1 | **物品与工具**（镐/斧/铲/剑 + 耐久 + 等级） | 没有工具，挖掘就只是"删方块"；工具是 MC 生存循环的支点 |
| 2 | **分级挖掘耗时** | `Block.hardness` 已经在方块表里躺了一版没用上；有了工具才有"该挖多久" |
| 3 | **掉落物**（挖了掉东西、走过去捡） | 把"挖"与"得到"分开，才有"素材 → 合成"的经济 |
| 4 | **合成**（工作台 3×3 / 熔炉烧炼） | 消费端；也第一次用上"多方块交互" |

## 二、数据模型（纯数据 + 纯函数，可 headless 单测）

### 2.1 物品表 `items.py`

```python
Item(id, name, title, *, stack=64, tool=None, tier=0, durability=0,
     block=None, fuel=0.0, food=0)
```

* `tool` ∈ `{'pickaxe','axe','shovel','sword'}`；`tier` ∈ `{1:木, 2:石, 3:铁}`；
* **方块也是物品**：`block=<block_id>` 表示"放下时变方块"（Phase 0 的 hotbar 语义保留）；
* 工具用 `durability`，放在**单独的工具实例**上（见 2.3）。

**id 契约与方块表同规**：只追加不改号（存档里存名字，不存 id）。

### 2.2 挖掘规则 `items.py::break_time(block, tool)`

```
t = hardness × (1.5 if 需要工具 else 1.0) / (工具速度 if 工具对路 else 1)
```

* 对路工具（镐挖石、斧砍木、铲挖土）→ 速度按 tier 递增（1×/2×/4×…）；
* 不对路 → 速度 1（赤手空拳），且**某些方块不掉落**（石类要镐）—— 与 MC 一致的"手感门槛"；
* 基岩 `hardness=999` ⇒ 永远挖不动（沿用 Phase 0 的判据）。

### 2.3 工具实例（耐久不能被堆叠掩盖）

堆叠物品是 `{item: count}`；**工具是"带状态"的**，所以背包里存
`ToolStack(item_id, durability)`（`count` 恒为 1）。存档写
`{"item": "iron_pickaxe", "durability": 132}`，读档时未知物品**响亮报错**。

### 2.4 掉落物 `drops.py`

```python
drops_for(block_id, tool) -> [(item_id, count)]
```

* 规则表 + 纯函数；石头→圆石、草→泥土、矿石→煤/铁（要镐）、树叶→偶发树苗；
* **不带工具就掉不了**的方块（石类）在这里表达，而不是散落在内核里。

### 2.5 合成 `recipes.py`

```python
Recipe(kind, pattern|inputs, output, count, table='craft'|'furnace', time=0.0)
craftable(recipe, have) -> bool
```

* 工作台：无序/有序两种（先做无序，有序留到有 3×3 UI 时再开）；
* 熔炉：`输入 + 燃料 → 产出`，带**烧炼时间**（内核按 dt 推进）；
* 配方表是**数据**；`cli` 里能列出全部配方并逐个可合成性自检（防"配方写了但永远做不出来"）。

## 三、内核改动（保持 Phase 0 的纪律）

* 玩家新增：`health`/`max_health`、`hunger`/`saturation`、`tools`、`drops`（世界里的掉落物实体）；
* `dig()` 语义升级：**按住左键累积耗时**（`dig_progress`），到点才真正破坏并产生掉落物；
* `place()` 升级：手持工具/物品时按物品语义处理（工具不放置、食物可吃）；
* 掉落物：`drops` 是 `[(pos, item, count, ttl)]`，每帧下落 + 靠近自动拾取；
* 饥饿：移动/挖掘消耗、`food` 回补；归零后掉血；血量归零 → `state='dead'`，重生清空；
* `auto_step()` 脚本扩展：砍树 → 合成木板 → 挖矿 → 烧炼 → 吃东西，跑完自证。

**接口兼容**：Phase 0 的 `dig()`/`place()`/`hotbar`/`inventory` 语义**保留**
（创造模式行为不变），新增能力走新方法 —— 老测试不该因为这一版而改判据。

## 四、验收（每条都要能跑、能对拍）

```
python -m tests.run_all          # 新增 items/drops/recipes/survival 四个模块
python -m mcclone3d.cli          # 新增 items / drops / recipes / survival 四条检查
python examples/mcclone3d.py --flag auto,verbose   # 自动机跑完整生存循环
python examples/shot_hud.py      # 目视：背包/合成/血条/饥饿条
```

判据（可量化，不说"看起来对"）：

1. **挖掘耗时**：木镐挖石头 < 赤手挖石头，且比值等于规则表算出的比值（数值对拍）；
2. **耐久**：挖 N 下后工具恰好断裂，且断在**第 N+1 下之前**（边界对拍）；
3. **掉落**：带镐挖石头掉圆石、赤手挖石头**不掉**（规则表逐条穷举）；
4. **配方**：每条配方都能用其输入合成出来（反向自检，防死配方）；
5. **熔炉**：烧炼时间按 dt 累积，且**与帧率无关**（30/60/120Hz 同一结果）；
6. **生存**：饥饿归零 → 掉血 → 死亡 → 重生后状态归位；吃东西回血回饥饿；
7. **存档**：工具耐久、血量、饥饿、掉落物**全部往返一致**。

## 五、不做（这一版刻意不碰）

* 有序 3×3 摆放（要 UI 交互，留到 UI 一起做）；
* 附魔/酿造/红石（Phase 3）；
* 生物与昼夜光照传播（Phase 2）——但 `health` 的"受伤来源"接口现在就留好，
  Phase 2 的生物只要调 `kernel.hurt(n, cause)` 即可。

### 6.1 执行中修掉的真 bug（都留了回归判据）

| # | 现象 | 根因 | 判据 |
| --- | --- | --- | --- |
| 1 | **熔炉一炉发货两次**：装炉那一刻产物就进背包，烧完再给一次（5 条烧炼配方全中） | `furnace_load()` 借 `recipes.craft()` 当"只扣不加"的扣料工具用，而 `craft()` 的语义含"加产出" | 新增 `recipes.consume()`（只扣不加），`craft()` 复用它；回归：装炉后背包**空**、烧完**恰好 1 个** |
| 2 | `input_options()` 抛 `AttributeError: 'int' object has no attribute 'split'` | 把 `inputs` 的键当数量、值当名字写反了（键是物品名、值是数量） | 改为返回 `[(数量, [名字...])]`，并有单测直接调它 |
| 3 | `dig_dt()` 到点返回 `(True, 'dirt')` 而不是 `('done', 'dirt')` | `_finish_dig` 的原始元组被直接漏出去，协议不一致 | `dig_dt` 统一包装；`dig()` 保持 `(bool, 名字)`，两者文档里写明刻意不同 |
| 4 | `torch` 挖了没有掉落（掉落表覆盖不全） | 加方块/物品时漏了掉落行 | CLI `drops` 检查**穷举全部方块**，缺一个就红 |
| 5 | `items.py` import 期 `NameError: TORCH` | 编辑中间态（把 `TORCH` 写进元组却没加进导入行） | 全仓 import 即崩，CI/测试会立刻发现 |
| 6 | `mcclone3d.kernel` 一挖就 `AttributeError: _mark_dirty` | Phase 1 重构时把该方法误删 | `_mark_dirty` 是网格重建的唯一入口，有单测盯着 |

> 教训（值得跨项目复用）：**"扣输入"和"加产出"必须是两个入口**。
> 只要有一处调用方把"合成的副作用"当成"扣料的工具"，就会静默多发一份产物 ——
> 而它在单机演示里几乎看不出来（背包多一个东西，谁会发现？）。
> 是 teammate 用最小复现抓出来的，所以 §四 的判据里"熔炉装炉端到端"这条**必须有**。
