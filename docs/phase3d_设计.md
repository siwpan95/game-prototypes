# Phase 3-D 设计稿：资源包式材质

> 范围：**用外部 PNG 覆盖程序化贴图，并允许换分辨率**（16/32/64px）。
>
> 这一批只碰"贴图像素从哪来"这一层 —— 玩法、存档、网格、UV **一个字节都不改**。
> 稿子的重点是四处"看着容易、做起来出事"的地方：
> **① UV 为什么与分辨率无关**（§三，这是整批最省事也最容易翻车的假设）；
> **② 色相旋转必须按窗口选择性做**（§五，第一版把砖墙染成了紫的）；
> **③ `bytearray[a:b] = 更短的 bytes` 会静默缩短**（§六，图集从 262144 缩成 157056）；
> **④ 为什么资源包不能新增贴图**（§二，也是 Phase 3 那条"UV 错位"教训的姐妹篇）。

---

## 一、模块与分工

| 文件 | 角色 |
| --- | --- |
| `mcpng.py` | **最小 PNG 编解码**（只用 stdlib `zlib`，不引 Pillow） |
| `packs.py` | 资源包：清单 / 加载 / 校验 / 解析 / 演示包生成 |
| `textures.py` | 加一层 `pack` 覆盖 + `layout_for(pack)`（可变分辨率图集） |
| `kernel.py` | `use_pack()` / `pack_report()`；配置树的 `pack:` 字段 |
| `mesh.py` | **一行都没改**（见 §三） |

`mcpng` 单独成模块的理由是"边界要写清楚"：PNG 里我们真正需要的子集很小
（8 位、非隔行、filter 0–4），剩下那些（16 位、Adam7 隔行）遇到就**响亮报错**。
为了读一张 16×16 的小图拖进一整个 Pillow，还会把"图集逐字节可复现"这条
从纯 Python 挪到一个二进制依赖上 —— 与本项目"磁盘上只有生成规则"的纪律相冲。

## 二、包格式，以及**两条硬约束**

```
packs/<id>/
  pack.json      {"name": …, "description": …, "resolution": 32}   # 全部可选
  tiles/*.png    # 想覆盖哪张就放哪张；没放的落回程序化基线
```

`pack.json` 可以完全不写（等价于"纯 PNG 目录，分辨率从第一张图推断"）。

**约束一：不能新增/删除贴图，只能覆盖已存在的名字。**
图集是**一张**均匀网格纹理，UV 由"格号 / 列数"算出来，而 `mesh.py` 在 **import 期**
就把这些 UV 烘进了顶点数据。新增一张 ⇒ 格号全变 ⇒ 已烘好的 UV 全错位。
症状不是"新贴图不显示"，而是"**整个世界都换成了别的贴图**"——
Phase 3 真踩过一次同款（`phase3_设计.md` §十，`ATLAS_COLS` 从 6 提到 8 时整个世界采样到红石贴图）。
所以 `load()` 遇到不认识的贴图名**直接报错，并把合法名字全部列出来**
（"我把 `stone` 拼成 `stoen`"是这里最常见的错，静默忽略 = 改了包却没生效）。

**约束二：一个包内所有贴图必须同分辨率。**
16px 和 32px 混在一张网格里，要么重采样（引入插值、破坏"逐字节确定"），
要么破坏 UV 假设。⇒ 不一致就报错。`resolution` 也必须是 **2 的幂**
（图集边长 = 列数 × 分辨率，mipmap 与老驱动都对 2 的幂最友好）。

**没被覆盖的贴图怎么办**：基线是 16px，包声明 32px 时，落回基线的那几张会
**按最近邻补到 32px**（`textures.scale_rgba`）。这条不做的话，"只覆盖一部分"就
不成立了 —— 而且不成立的方式很糟（见 §六）。

## 三、分辨率变了，`mesh.py` 为什么一行都不用改

这是本批最值得单独写出来的一点：**UV 矩形是归一化的，`tile` 会被约掉**。

```
u0 = 列号 × tile / (列数 × tile) = 列号 / 列数
```

16px 的包与 64px 的包，**UV 完全相同**，只有上传给 GL 的那张纹理的像素尺寸变了。
⇒ 换分辨率只影响 `build_atlas()` 的输出与纹理上传；几何、UV、面剔除、光照顶点色
一个字节都不动。CLI 的 `pack` 检查正是盯着这条：
同一区块在带包/不带包下，`positions` / `uvs` / `colors` 逐字节相同。

**反过来说，这句话把一处隐患点了出来**：既然"尺寸"和"数据"分居两处，
那就必须**同源**。`textures.LAYOUT.size` 恒为 `8×16=128`，
而带 32px 包时图集边长是 `8×32=256`。上传纹理时拿了前者、喂了后者的字节，
GL 就会按 128×128 去读一份 256×256 的数据 ⇒ **整片花屏**。
所以 demo 里那两处都走 `layout_for(pack)` —— 这是"常量与数据必须同源"那条纪律的又一例。

## 四、PNG 编解码：两个必须写明的坑

1. **filter 是逐行的，参考行是"上一行的原始（未过滤）字节"。**
   这里说的"上一行"是**已反过滤后的输出行**，不是压缩流里的原始行。写反了的话，
   图像**前几行完全正常、越往下越偏**，看着只像"噪点有点大" —— 肉眼极难发现
   （第 1 行无论哪种理解都一样，很多实现就靠"第 1 行对得上"侥幸过关）。
   ⇒ 所以本模块的判据是**编码→解码往返逐字节一致**，
   再加上一个独立写就的**正向 filter 实现**对拍（`test_mcpng` 的 `_forward_filter`）。
2. **PNG 的 α 不是预乘的**，与 `textures._Canvas` 同一口径，不需转换；
   但 **type 2（真彩，无 α）必须补 `a=255`** —— 忘了补，资源包里的不透明贴图
   会变成**全透明**（图集里看着像"这个方块消失了"）。

顺带支持了调色板（type 3，位深 1/2/4/8 + `tRNS`）：真实资源包多半是美术用工具导出的
索引色小图，"拿一张现成图当贴图"是最自然的用法，不支持就直接撞墙。

## 五、演示包：色相旋转**必须按窗口选择性做**

演示包从程序化基线**现算**（仓里不带二进制：`packs/` 进 `.gitignore`），两种风格：

* `autumn` —— **32×32**（2× 最近邻 + 细噪）+ 把**绿**的像素转 -0.25（绿→橙红）；
* `retro`  —— **16×16**（不动分辨率）+ 每通道压到 4 档。

这里踩了本批最实的一个坑。**第一版对整张图做色相旋转**，结果：

* `log_side` / `log_top` 底色 h≈0.088（暖木色），转 -0.25 落到 **h≈0.84（洋红/紫）**；
* `crop` 的金黄同理，`water` 的蓝会变绿；
* 截图里砖墙、木料、平台上的 `log_top` **全变紫红**，一眼假。

改成"只染绿的那几张贴图"还不够 —— **`grass_side` 同一张图里既有草（绿）又有土（棕）**，
整张转会把土也染紫，于是梯田侧面出现**一圈紫色腰带**。

最终做法：`_hue_shift(…, window=AUTUMN_WINDOW, soft=…)`
—— 只对**原色相落在窗口内**的像素转，窗口边缘留过渡带。

* 好处一：连"该染哪几张贴图"的白名单都不需要了。一张图里绿的变秋色、其余原样。
* 好处二：这也顺手解决了 `s≈0` 的灰度像素（石头）—— 色相对灰没有意义，
  硬转会凭空引入颜色。
* `soft` 过渡带不是装饰：噪声贴图的色相天然在窗口边界附近抖动，
  硬切会把一张草地切成"转了/没转"的**棋盘格斑点**。

判据不能是"截图看着像不像秋天"（紫色草地看着也挺"有风格"），
而要断言**色相落在哪**：草地 `h: 0.29 → 0.04`（橙红区间），
`grass_side` 里草像素变暖、土像素的 h 变化 < 0.04。

## 六、一个静默缩短的陷阱（`bytearray` 切片赋值）

```
out[row_dst : row_dst+stride] = px[row_src : row_src+stride]
```

`bytearray[a:b] = 更短的 bytes` **会把 bytearray 缩短，不报错**。

带着 32px 的包却被塞进 16px 的几何时，`px` 的行只有 64 字节而 `stride=128`，
于是每写一行图集就短 64 字节 —— 实测图集从 `262144` 缩到 `157056` 字节。
它不会在 `build_atlas` 里爆，而是等到 GL 拿到"尺寸与数据对不上"的纹理才**整片花屏**
（正是 §三 那个"尺寸与数据必须同源"的另一种发作方式）。

修法是两层的：① 逐张核对 `len(px) == w*h*4`（核对**实际字节数**，
而不是核对几何自己给的 `w/h` —— 那等于没核）；② 收尾再断言一次图集总长没变。

## 七、资源包**不进存档**

与 MC 同口径：资源包是**客户端外观设置**，不是世界数据。
换个包读同一份档，必须还是同一个世界。`test_kernel` 里有一条专门钉它：
挂包前后 `json.dumps(k.dump())` 的字节**完全相同**。

`pack` 也不写进 `SAVE_VERSION` —— 存档版本号只随"世界语义"变。

## 八、验收（全部实跑）

```
python -m tests.run_all --quiet              # 20 模块 316 项（零 GL）
python -m mcclone3d.cli                      # 21 条 headless 验收
python examples/mcclone3d.py --smoke 3       # 真窗口冒烟（--pack autumn 同样过）
python examples/make_pack.py                 # 生成演示包（程序化，确定性）
python examples/shot_pack.py                 # 目视：无包 / autumn / retro 三张
```

`cli` 的 `pack` 条盯着八件事：基线不变 / 32px 图集 = 256px / **UV 不变** /
覆盖生效 / 未覆盖补分辨率 / 几何与顶点色不变 / 报告说得清 / 坏包报错 3/3。

**目视判据（可量化，不靠"看着像")**：三张图同机位、同世界、同时刻（正午）、同天气（晴）
—— `shot_pack` 清出一条**观察走廊**并固定这些变量，所以取景逐像素一致。
用 `mcpng` 自己读回三张图做逐通道比较：

| 对比 | 完全相同像素 | 差 > 60 的像素 | 平均差 | 说明 |
| --- | --- | --- | --- | --- |
| 无包 ↔ autumn | 25.0% | **27.7%** | 29.9 | 草木整片改色，其余（石/砖/矿/水）不动 |
| 无包 ↔ retro  | 23.1% | **0.00%** | 12.6 | 色相不变，只有 4 档量化的误差 —— **没有任何结构差异** |

`retro` 那行是这张表里最有信息量的一条：**没有一个像素差超过 60**，
说明差异纯粹来自"像素值被量化"，几何/UV/取景完全一致。
（这个量化口径也解释了为什么远处某些像素的颜色看着"跑偏" —— 图集 mip 是
`GL_NEAREST_MIPMAP_LINEAR`，缩小时会在两级 mip 之间做线性混合，
把相邻格的颜色平均进来。）

## 九、这一批不做（已知边界）

* **不做 UI 热重载**：换包要重建纹理（demo 走 `--pack` 参数，在 `_setup_gl` 之前生效）。
  运行期热切换是另一件事（要处理"已上传的纹理对象怎么换"），本批不做。
* **不支持 16 位 PNG / Adam7 隔行 / 动画 PNG**：遇到**响亮报错**，不静默给半个答案。
* **不支持 `pack.mcmeta` 那套格式**：本仓是机制致敬，不声称兼容任何具体格式。
* **不做贴图混合/叠加层**（MC 的 `overlay`）：一个名字一张图，覆盖是替换而非叠加。
