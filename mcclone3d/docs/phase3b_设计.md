# Phase 3-B 设计稿：元件 tick 队列 + 红石火把反相器

> 范围：**元件 tick 队列**（中继器延迟 4 档）、**红石火把变反相器**、由这两者凑出的**环形时钟**。
> 另外附带一件不属于红石的事：**引擎上了 PyPI**（`pip install 3dworld`）之后的接入改造（§八）。
>
> 这份稿的重点是 §三（惰性求值 = 脉冲整形）与 §七（七条实测踩坑，其中三条是"通过测试但行为错"
> 的隐性 bug）。上一批（`docs/phase3_设计.md`）的红石是**纯瞬时**的：一次重算迭代到固定点，
> 输出立刻变 —— 那一批因此**做不出任何带时间的东西**。

## 一、为什么要引入 tick 队列

上一批的引擎结构是"**按网络重算 + 迭代到固定点**"：从变化点出发收集整个元件网络，
每轮"清空 → 传播 → 切输出"，直到输出不再变化。这个模型对**瞬时**元件（灯、门、活塞）完美，
但它有一个隐含前提：**元件状态只依赖当前布局**。

于是：

* 拉杆一开，灯在同一帧就亮 —— 无论线有多长、中间隔了几个中继器；
* 任何**短于一个重算周期**的输入都会被拉平成"有/无"，**脉冲形不出来**；
* 更根本的：**时钟做不出来**（没有"上次的状态"这个概念，环里的一切都在同一轮里算完）。

引入**元件 tick 队列**就是为了把"延迟"从迭代里挪到**时间轴**上。

## 二、队列的设计（三条硬约束）

`PowerGrid.events` 是最小堆 `(到期时刻, 入队序号, 格子)`，配一张去重表 `sched: 格子 → 到期时刻`。

1. **去重**：同一格同时只挂一个待触发事件。
   固定点迭代每轮都会看到"输入与输出不一致"，不去重会排一堆同刻事件。
2. **自增序号打破同刻并列** ⇒ 处理顺序不依赖 `set`/`dict` 的迭代顺序 ⇒ **可重放**
   （时钟的"逐帧波形完全一致"这条单测靠它）。
3. **`TICK_EVENTS_CAP` 护栏**：环形结构会**源源不断**产生事件，超限时**响亮抛错**
   （`RedstoneOverflow`，同 `LightOverflow` 的思路：绝不静默截断 —— 静默截断会表现为
   "红石偶尔不动"，那种 bug 最难查）。

中继器**不再**在 `_apply_outputs` 里翻转，而是 `_schedule(cell, delay)`；
瞬时元件（灯/门/活塞/火把）仍在固定点迭代里立刻结算。
两边一分家，"迭代到固定点"就能在"中继器正等着翻转"时正常收敛。

## 三、触发时**重新读世界**（惰性求值）= 脉冲整形

队列里只存 `(到期时刻, 格子)`，**不存"该变成什么"**。触发时按**当前**输入重新判断：

```
want = 背面有电吗      # 现在读
if want != 当前状态: 翻转
```

**为什么必须这样**：延迟期间输入可能已经变回去（短脉冲）。存"目标状态"的话，
队列会忠实执行一个**现实中不存在的脉冲** —— "按下再松开，0.4 秒后灯还是闪了一下"。

于是"脉冲整形"是这个设计的**副产品**，不需要额外规则：

| 输入脉冲 | 与档位延迟比较 | 结果 |
| --- | --- | --- |
| 0.1s（按钮快速按一下） | 短于 0.3s 档 | **输出无脉冲**（灯全程不亮） |
| 0.6s | 长于 0.3s 档 | 照常输出（延迟 0.3s 后亮） |

对照组的用例是必须的：只测"短脉冲被吃掉"，看不出中继器是不是**彻底坏了**。

## 四、档位为什么必须进 id（4 档 × 4 方向 = 32 个 id）

方块只有 `id`、没有额外的元数据字段，而"延迟多久"是玩法本身 ⇒ 档位只能落在 id 里。

* 档 0（0.1s）**沿用历史名字**：`repeater_north_off` / `repeater_south_off`…；
  档 1~3 是 `repeater_<方向>_d<n>_<态>`。
  ⚠ 实测：把档 0 的 `north` 名"顺手简化"成 `repeater_off`，当场撞红
  "别名表里的每个名字都必须是方块名"那条断言 —— 它守的正是**存档契约**
  （老档里的中继器会变成未知方块）。
* `MAX_ID` 从 63 提到 **80**。⚠ 有单测钉着"**id 连续无空洞**"
  （`sorted(BLOCKS) == 1..N`）⇒ 这个数**必须等于当前最大 id**，不能"留余量"。
* 别名表（32 个状态名 → 同一件物品 `repeater`）**由表生成**：
  手写 32 行必漏，而且漏了不会报错，只会让"挖掉一个 3 档中继器"什么都不掉。

玩家右键中继器 = **调档**（1→2→3→4→1），**不改开/关** ——
亮灭是信号算出来的，给玩家手动切的入口只会和信号打架（下一帧就被纠正，看着像"点了没反应"）。
`toggle_repeater()` 保留但只给测试/调试用。

## 五、红石火把变**反相器**（"强充能"的口径）

初版火把只是个"常亮电源"。现在它是反相器：**脚下那块被强充能时自己熄灭**
（`redstone_torch` ↔ `redstone_torch_off`，两个状态 id 各有一张贴图）。

**什么算强充能**（`strongly_powered`）—— 只有**元件**能强充能：

* 六邻里有 `LEVER_ON` / `BUTTON_ON` ⇒ 本格被强充能
  （⚠ 简化：真实 MC 里拉杆只充能它**附着**的那一块；本项目没有"附着"概念，
  按六邻算。这个放宽只会让火把更容易熄灭，**不会**造成自锁）；
* 六邻里有 `REPEATER_ON` 且**本格就是它的正面那一格** ⇒ 被强充能。

**红石线只能"弱充能"**（它不给方块强充能）—— 这一条是**反相器不自锁的全部原因**：

```
错误做法（会自锁）：火把"六邻有电就熄灭"
  火把亮 → 自己邻居的线有电 → 判定"有电" → 熄灭 → 没电 → 亮 → …
  ⇒ 固定点迭代**永不收敛**（只能靠 MAX_ITER 截断，留下一个任意的状态）

现在的做法：火把只看**脚下**是否被元件强充能
  火把的输出只能进红石线（弱充能）⇒ 永远改不动自己的睡眠条件 ⇒ 结构上不可能自锁
```

这条不变量有**独立单测**（`t_wire_does_not_strongly_charge`）：通电的线旁边的石头
`strongly_powered` 必须是假，换成中继器正面才为真。

## 六、时钟：反相器（瞬时）+ 中继器（延迟）= 环形振荡

装置就三样：**中继器朝南 → 正面一块实心块 → 块上的火把 → 线绕回中继器背面**。

```
R 亮 ⇒ 强充能正面那块 S ⇒ S 上的火把 T 熄灭（瞬时）
     ⇒ T 的线断电 ⇒ R 的背面没电 ⇒ 排队：R 0.1s 后熄灭
R 灭 ⇒ S 不再被充能 ⇒ T 亮（瞬时）⇒ 线通电 ⇒ R 背面有电 ⇒ 排队：R 0.1s 后点亮
```

**周期 = 2 × 档位延迟**（0.1s 档 ⇒ 5Hz；0.3s 档 ⇒ 约 1.67Hz）。
实测：1 档 3.0s 内灯翻转 **29 次**（理论 30），3 档 **10 次**（理论 10），
两次跑的**逐帧波形完全一致**。

灯接在"中继器背面那条线"上，所以它**与火把反相**地闪 —— 这也让"时钟在跑"这件事
在读数上看得见。

## 七、这一批踩的坑（三条是"测试通过但行为错"的隐性 bug）

1. **幽灵信号**（最隐蔽）：`power` 里过期格没人清。原先只在"网络成员"里清，
   而"关着的按钮""被挖掉的线"**不是**网络成员 ⇒ 原地留下信号。
   症状：按钮 0.1s 回弹后，中继器背面**仍读到 15**，把短脉冲当成了常亮。
   修法两处：`_write()` 里"新方块不是元件就把这格的信号作废"（**立刻**生效，
   因为 `_fire_due` 跑在 `_clear` 之前），`_clear()` 里顺带全局清理非法条目。
2. **中继器每翻一次掉档位**：`repeater_on_id()` 返回的是 `REPEATER_BY_DIR[dir][1]`
   —— 那是**档 0** 的 id（加档位之前看不出问题）。
   症状：3 档时钟"第一次延迟 0.3s，之后就变成 0.1s"（周期 0.6s → 0.2s）。
3. **浮点相位滑移**：`now` 是逐帧累加的浮点，累到几百帧后会比重排时刻**略小**
   （`0.05×N` 在两条路径上差 1 ulp）⇒ 严格的 `due <= now` 让事件**晚一帧**触发；
   而晚一帧不是"抖一下"，它把后续全部推后 ⇒ **相位永久漂**（实测 0.2s 周期漂成 0.3s）。
   修法：比较留 `1e-6` 容差，并加一条"长跑 8 秒翻转次数不漂"的回归。
4. **`mark()` 只标一层不够**：火把的睡眠条件看的是"**脚下那格**是否被强充能"，
   而强充能又取决于脚下那格的**六邻** ⇒ 变化点自己 + 它的六邻这 7 格的**上方**若有火把，
   也必须重算。漏掉这一层 ⇒ 中继器亮了、块上的火把**不翻**（反相器死活不工作）。
5. **截面截图调了 4 版**：斜视角下"1/8 格高的红石线"会被看成一大块红板、火把与中继器互相遮挡。
   最终用**垂直俯视**（每一格摊平，最好判读）。教训：拍小装置，机位要按**装置尺寸**给，
   而且"画面里只有装置"比"有参照物"重要得多（前三版都被树/房/山坡抢走注意力）。
6. **测试场景本身没搭对**（三条，都是一眼看上去像实现坏了）：
   裸放一个 `REPEATER_ON` 会被引擎按"背面没电"当场判灭（所以测"强充能"必须给它背面接拉杆）；
   "跑整数个周期后状态不同"不能用来判"在闪"（1.0s 正好 5 个周期，灯回到同态）；
   `use()` 的射线打在**脚底那层**会从方块头顶飞过去（`pos` 是脚底，眼睛在 +1.6）。

## 八、顺带：引擎上了 PyPI 之后的接入改造

`world3d` 现在**是** PyPI 包（发行名 `3dworld`），所以：

* `requirements.txt` / `pyproject.toml` 正式写上 `3dworld>=0.1.0,<0.2`；
* **查找优先级倒过来**：`MC3D_ENGINE_ROOT`（本地检出）**优先**于已安装的包。

⚠ 为什么必须倒过来：原先的顺序是"先 `import world3d`，失败才看环境变量"。
引擎没上 PyPI 时这没问题；**上了之后**，只要 `pip install -r requirements.txt` 装过包，
"先 import"那条**永远成功** ⇒ `MC3D_ENGINE_ROOT` 变成一句被静默忽略的摆设：
开发者以为在测本地改动，实际测的是**发布快照**（"测量的代码 ≠ 提交的代码"）。

再加一道**影子检查**：设了 `MC3D_ENGINE_ROOT` 却加载到那个目录之外
（多半是 `world3d` 已被 import 过、包抢先，Python 的模块缓存换不掉），
**响亮抛错**并给出两条修法，而不是默默用别的引擎。

## 九、验收（全部实跑）

* 单测 **18 模块 273 项**（`test_redstone` 从 18 项增到 **34 项**）：
  延迟（0.2s 不翻 / 0.35s 翻）、惰性求值（短脉冲被吃 + 长脉冲照常的对照组）、
  四档数值与 32 个 id、调档循环且不改开关、**翻转不掉档**、**无幽灵信号**、
  反相器（亮→灭→复亮）、**线只弱充能的不变量**、时钟（1 档 ≈30 次/3s、3 档 ≈10 次）、
  **逐帧确定性**、**8 秒不漂相位**、队列去重、`TICK_EVENTS_CAP` 护栏、
  `run_until_stable`（静态会停 / 时钟不停）、内核 `use()` 调档；
* headless **19 条**（新增 `tickqueue`）：延迟三判据 · 短脉冲被吃 · 长脉冲照常 ·
  四档 · 调档循环 `[0,1,2,3]` · 反相器三判据 · 线只弱充能 · 时钟 1 档 29 次/3s ·
  3 档 10 次 · 逐帧确定性 · 8s 不漂（79 次）· 一直挂着事件 · **1 秒时钟耗时 1.1ms**；
* **PyPI 引擎独立验证**：干净 venv 只装 `requirements.txt`、**不设** `MC3D_ENGINE_ROOT`
  ⇒ 18/18 模块 273 项 + 19 条 headless **全过**（证明发布快照够用）；
  另验本地检出优先、以及"包抢先"时影子检查确实抛错；
* 目视：`shots/phase3b_inverter_off.png` / `_on.png`（同机位俯视）——
  关：左线暗 / 右线亮红 / 灯**亮黄**；开：左线亮 / 右线暗 / 灯**暗棕**。
  即"火把被强充能而熄灭 ⇒ 反相"。

## 十、这一批不做（已知边界）

* **中继器之外的元件没有延迟**（灯/门/活塞仍是瞬时；MC 里它们各自有 tick 延迟）；
* 没有**比较器 / 侦测器**（做脉冲发生器、容器读取要它们）；
* 时钟**没有占空比控制**（只有"反相器 + 延迟"这一种形态）；
* 拉杆/按钮**不区分附着方向**（按六邻强充能，见 §五的简化说明）；
* 中继器四个朝向共用同一张贴图（朝向只体现在**功能**上）。
